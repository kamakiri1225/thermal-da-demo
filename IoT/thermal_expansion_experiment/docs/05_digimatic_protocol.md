# 05. Digimatic/SPC信号の扱い

更新日: 2026-07-27
**このドキュメントの多くの項目は実機・実信号での確認が前提。安易に断定していない箇所を「要確認」「要実機確認」「要信号波形確認」と明記している。**

## 5.1 前提の整理

- ミツトヨのDigimatic/SPC出力は、**一般的なUART（調歩同期シリアル）ではない**。DATA線とCLOCK線を使ったシリアル的な信号だが、ボーレート・フレーム構成・信号レベルは通常のUARTと異なる。
- 電圧レベルは**約1.5V系である可能性が高い**という情報がある（公開情報ベース）。ESP32は3.3Vロジックのため、レベルの整合性を実測で確認する必要がある（**要信号波形確認**）。
- 公開されている実装例（MGX3D/EspDRO、Roger-random/mitutoyoリポジトリ、各種Arduino Digimatic関連記事、Mitutoyo Digimatic SPC protocolの解説等）は存在するが、**それらが543-790B-10と無条件に組み合わせて動作する保証はない**。型番・世代によりピン配置や細かい仕様が異なる可能性がある。

## 5.2 安全のための設計方針（必須）

1. **最初はインジケータ自身の電池で動かす。** ESP32からインジケータへ給電しない。
2. ESP32とインジケータの**GNDは共通化**する。
3. **DATAとCLOCKのみ**ESP32へ入力する（ESP32からは出力しない）。
4. **SPC信号端子へ3.3Vを直接印加しない。**
5. **入力ピンをOUTPUT HIGHにしない。** ファームウェアは該当ピンを常に`INPUT`（`INPUT_PULLUP`も含め出力方向にしない）として扱う。
6. SPC信号は一般的なUARTとして扱わない（ハードウェアUARTペリフェラルに直結しない）。
7. 電圧レベルが不明な場合は、ADCによる電圧確認、コンパレータ、トランジスタ、レベル変換回路の追加を検討する。
8. 直接接続の安全性が確認できない場合は、保護回路（抵抗分圧・ツェナーダイオード・レベル変換IC等）を追加する。

## 5.3 ピン割当（案、`04_electrical_wiring.md`と重複掲載）

| 役割 | ESP32ピン | 備考 |
|---|---|---|
| SPC DATA | GPIO34 | 入力専用。内部プルなし |
| SPC CLOCK | GPIO35 | 入力専用。内部プルなし |
| GND | 共通 | |

GPIO34/GPIO35は入力専用ピンであるため誤ってOUTPUTに設定するリスクを避けやすいという利点で選定している。ただし内部プルアップ・プルダウンがないため、**必要な外付け抵抗値・向き（プルアップ/プルダウン）は信号実測後に確定する**（**要確認**）。

## 5.4 事前確認手順（通電前に必ず実施）

1. 純正ケーブルを加工する場合、**切断前に**テスターで導通・端子位置を確認する。GND/DATA/CLOCKがどの線に対応するかを、ケーブル内の**線色だけで判断しない**（型番・ロットで配色が異なりうるため）。
2. 可能であれば、純正ケーブルを完全に切断せず、**中継基板・変換アダプタ**を作る方法を優先する（元のコネクタ形状を保てば、後で別の用途にも転用しやすい）。
3. インジケータを単体（電池のみ）で動作させ、表示が正常に変化することを確認する。
4. テスターで、DATA/CLOCK線の電圧レベル（Hi/Lo）をおおまかに確認する。
5. 可能ならロジックアナライザで、CLOCK/DATAの波形（周波数、パルス数、アイドル時間、フレーム周期）を取得する。
6. 可能ならオシロスコープで、電圧振幅（0V〜何V相当か）を確認する。
7. 上記で得た実測値をもとに、本ドキュメントのピン割当・保護回路の要否・後述のデコード実装のパラメータを確定させる。

## 5.5 想定されるフレーム構成（一般に説明される概要、未検証の仮案）

公開情報で一般に説明されているDigimatic/SPCのデータ転送は、おおむね以下のような構成とされる（**出典により細部が異なり、本プロジェクトでは未検証**）。

- CLOCKの立ち上がり/立ち下がりエッジに同期して、DATAが1ビットずつ出力される。
- 1回の送信は、符号・BCD化された数値の各桁・小数点位置・単位（mm/inch）などを含む、数十ビット（文献により52ビット前後、あるいはそれ以上とされる）のフレームとして送られる。
- 送信は連続的ではなく、バースト的に行われ、フレーム間にアイドル区間がある（測定値が更新されるたびに送信される、または一定周期で送信される、など機種依存とされる）。
- 一部の機種では、受信側（ESP32側）からREQ（要求）信号を出す必要があるとされる。

**本プロジェクトの方針:** 上記の詳細ビット割当をそのまま信じてハードコードするのではなく、まず「生ビット列をそのまま記録・出力するデバッグモード」を実装し、実測波形と突き合わせながらビット割当を確定させるアプローチを取る（`firmware/src/digimatic_reader.cpp`参照）。

## 5.6 ソフトウェア実装方針

`firmware/src/digimatic_reader.cpp`は以下の2段構えで実装している。

1. **RAWキャプチャモード（第一段階、必須の動作確認手段）**
   - CLOCKピンの変化に割込み(`attachInterrupt`)を設定し、エッジごとにDATAピンの状態を1ビットとしてバッファへ格納する。
   - 一定時間（タイムアウト、初期値50ms、`config.h`で変更可）CLOCKの変化がなければ「1フレーム受信完了」とみなし、蓄積したビット列をシリアルへ16進数/ビット列として出力する。
   - これにより、ロジックアナライザを持たない場合でも、ソフトウェア側の記録と実機の表示値を突き合わせて、フレーム長・ビット順のあたりをつけることができる（ただし電圧レベルの確認にはテスター/オシロが必要な点は変わらない）。

2. **BCDデコードモード（第二段階、要調整）**
   - 5.5節の一般的な構成を仮定した、ビット位置設定可能なデコード関数を用意する。
   - ビット位置・ビット順・符号ビット位置・小数点位置ビット・データ長は、すべて`config.h`の定数として切り出してあり、実測結果に合わせて調整できるようにしている。
   - 妥当なデコード結果が得られない間は、`spc_valid`フラグを0のままとし、CSVの`indicator_mm`/`disp_mm`はNaN扱いとする（誤った値を「もっともらしい数値」として記録しないため）。

## 5.7 未確定事項（このドキュメントに関するもの）

- Digimatic信号の電気仕様（電圧振幅、Hi/Loレベル、オープンドレインかどうか）: **要信号波形確認**
- ESP32へ直接入力してよいか、保護回路が必要か: 上記確認後に判断
- REQ信号線の要否: **要信号波形確認**
- 正確なビットフレーム構成（ビット順、符号・小数点ビットの位置、フレーム長）: **要実機確認**（5.6節のRAWキャプチャモードで解析）
- 543-790B-10と905338ケーブルの正式な適合: **要メーカー仕様確認**

これらが確定するまでは、`disp_mm`/`indicator_mm`の値は参考値として扱い、実験の合否判断には温度データや治具の予備試験結果とあわせて総合的に判断すること。
